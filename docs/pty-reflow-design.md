# PTY 幅変更時のテキスト追従（reflow）— 設計メモ

Status: **設計検討（未着手）** / 作成: 2026-06-11

Claude Code パネルの幅を変えたとき（パネル最大化、エディタ開閉、ウィンドウリサイズ）、
過去の出力テキストが新しい幅に追従しない問題の分析と実装方針。

## 1. 問題の正確な定義

「テキストが幅に追従しない」は実際には**性質の異なる 2 つの問題**の重なりであり、
混ぜたまま議論すると解けない。

| | 原因 | 例 | 解けるか |
|---|---|---|---|
| (a) 端末ソフトラップ | 行が端末幅を超えて**端末側**で折り返された | shell での長いコマンド出力 | 解ける（端末側の知識で再折返し可能） |
| (b) アプリのハード改行 | **アプリ自身**が幅を見て `\r\n` を書いた | Claude Code の会話トランスクリプト | **端末層では原理的に解けない** |

(b) が本丸である点に注意。Claude Code は自分で端末幅を取得してテキストを整形・改行して
出力する。端末（= Conductor の vt100 層）から見ると、それは「幅ちょうどの普通の行」で
あり、ソフトラップ情報を持たない。**これは kitty / iTerm2 / Ghostty などの実端末でも
同じで、リサイズしても Claude Code の過去トランスクリプトは再折返しされない。**
SIGWINCH を受けたアプリが再描画するのは可視領域（live region）だけで、スクロール
バックは描き直さない。

## 2. 現状実装（コミット d6b9639）

`pty_manager.rs` の `resize_session()` は幅変更時に **raw byte 履歴のリプレイ**で
vt100 パーサを再構築する:

- セッションは `raw_history: Option<VecDeque<u8>>`（上限
  `MAX_RAW_HISTORY_BYTES = 2MB`、行頭アライン付きトリム）に PTY 出力の生バイトを蓄積
- 幅が変わったら `rebuild_parser(&history, rows, cols, scrollback)` で新しい幅の
  パーサに全履歴を再パース。vt100 が新幅でソフトラップし直すので
  **shell 出力の (a) は解決済み**
- **fd98f14 以降、記録は `SessionKind::Shell` のみ**。Claude Code はカーソル
  アドレッシング＋ハード改行で自前整形するため、リプレイしても旧幅レイアウトを
  忠実に再現するだけ（reflow 効果ゼロでメモリ/CPU だけ消費）と判断され、記録自体を
  スキップ。Claude セッションのリサイズは `set_size()` + SIGWINCH（実端末と同じ
  挙動）に倒している
- 行数のみの変更は `set_size()`（vt100 が正しく処理する）

### 現状の限界（= まだ「追従しない」と感じる理由）

1. **Claude パネルには (a) の経路すら無い（意図的）**: リプレイは Claude Code の
   出力に原理的に効かないため fd98f14 で無効化された。つまり Claude
   トランスクリプトの幅追従は**端末エミュレーション層では手詰まり**で、
   別レイヤーで解く（§3-C）のが唯一の道。
2. **(b) には無力**: リプレイされるのは「旧幅向けにアプリが整形したバイト列」で、
   アプリが書いたハード改行はリプレイしても動かない（これが 1 の理由）。
3. **2MB 上限**（shell）: 長いセッションでは古い履歴が切り捨てられ、
   リプレイ後に先頭が消える。
4. **コスト**（shell）: 幅変更のたびに最大 2MB の再パース（同期、`screen` ロック
   保持）。頻度はパネル最大化・エディタ開閉・ウィンドウリサイズ時のみだが、
   リサイズドラッグ中は連発し得る。

## 3. 選択肢の評価

### A. raw リプレイの改善（現方式の延長）
- 内容: リプレイ時にカーソルアドレッシング系シーケンスをフィルタ/正規化する、
  履歴上限を引き上げる、リサイズをデバウンスする
- 効果: 限界 2〜4 を緩和。**(b) は解決しない**
- コスト: 小。ただしエスケープシーケンスのフィルタは「どこまで消すか」の
  ホワックアモールになりがち
- 判断: デバウンス＋上限見直し程度の小修正のみ価値あり。フィルタ深追いは非推奨

### B. vt100 → alacritty_terminal / wezterm-term への移行
- 内容: リサイズ時のソフトラップ reflow をネイティブ実装している端末エンジンに置換
- 効果: (a) をリプレイなしで堅牢に解決（wide char・カーソル痕も実端末品質）。
  **(b) は解決しない**（実端末と同じ挙動になる、が上限）
- コスト: 大。`pty_manager.rs` / `ui/common.rs`（vt100→ratatui 変換）/
  `media_state.rs`（ANSI パース流用）が全て vt100 型に依存
- 判断: 「(a) の品質問題・リプレイ痕が実害として頻発する」場合の選択肢。
  (b) が本丸である以上、これ単体では体験は大きく変わらない

### C. セマンティック・トランスクリプト再描画（本命）
- 内容: Claude Code の過去トランスクリプトを **PTY のスクロールバックから読むのを
  やめ、セッション JSONL（`~/.claude/projects/<proj>/<session>.jsonl`）から
  Conductor 自身が任意幅でレンダリングする**。
  - スクロール時（scroll_offset > 0）: JSONL 由来の「トランスクリプトビュー」を表示。
    幅変更時は再レンダリングするだけ — **(b) を含め完全に追従する**
  - 通常時（offset == 0）: 現行どおり PTY の live screen（入力ボックス含む）を表示
- 既存資産が揃っている:
  - `claude_sessions.rs` — worktree からセッション JSONL を特定するロジック（resume 用に実装済み）
  - `ui/markdown.rs` — 幅指定でのワードラップ付き markdown レンダラ（テーブル・多バイト対応）
  - `file_watcher` / 既存のポーリング基盤 — JSONL の追記検知
- 副次効果: 再折返しだけでなく、過去会話のシンタックスハイライト・role 別の色分け・
  検索など「rich mode」方向の拡張余地がそのまま開く
- コスト: 中〜大。新 UI ステート（transcript view のスクロール位置と PTY スクロール
  バックの統合）、JSONL のストリーミングパース、PTY 側スクロールとの切替 UX
- リスク / 未解決:
  - JSONL に「画面に出たもの全て」が入っているわけではない（ツール実行の生出力等は
    要確認。tool_use / tool_result イベントの表示ポリシーを決める必要がある）
  - shell パネルには適用できない（shell は (a) のみなので現方式で十分）
  - スクロール体験の連続性（PTY live → transcript view の境目）の設計が必要

### D. PTY 幅の固定・量子化
- 内容: Claude セッションの PTY を常に固定幅（例: 最大化時の幅）で動かし、
  狭いパネルでは水平スクロール or 切り詰めで表示
- 判断: **不採用**。狭い表示が常時壊れる方が体験が悪い

## 4. 推奨方針

**フェーズ 1（小、shell 向け現方式の仕上げ）**
1. リサイズのデバウンス（ドラッグ中の連続 rebuild を 1 回に）
2. `MAX_RAW_HISTORY_BYTES` をスクロールバック設定（`active_scrollback`）と整合する
   サイズに見直し
3. リプレイ後の既知の痕（あれば）をスクリーンショット付きで issue 化し、
   A のフィルタ深追いはしない

（注: fd98f14 で Claude セッションは記録対象外になったため、フェーズ 1 は shell
パネルの品質仕上げのみ。Claude パネルの幅追従はフェーズ 2 が唯一の道）

**フェーズ 2（本命、C を実装）**
1. Spike: 対象セッションの JSONL を読み、`ui/markdown.rs` で幅 N にレンダリング
   して既存ビューアに流す PoC（読み取り専用、トグルで表示）
2. スクロールバック統合: Claude パネルで `scroll_claude > 0` になったら
   transcript view に切り替え、`Shift+End` / 末尾到達で PTY live に戻す
3. tool_use / tool_result の表示ポリシー決定（折りたたみ表示が有力）
4. 幅変更時は transcript view を再レンダリング（これで (b) が解決）

**B（端末エンジン移行）は保留** — フェーズ 2 完了後、(a) 系の表示品質が
まだ気になる場合にのみ再評価する。
