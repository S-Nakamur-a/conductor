## 時計の注入 (`regenerate`)

`Regenerator` と `Job` が `Clock` を持つ。`Clock` は `Arc<dyn Fn() -> Instant + Send + Sync>` の
newtype で、既定は `Instant::now`。差し替えは `#[cfg(test)] Regenerator::with_clock` だけが行う
(公開 API は増えていない)。時計を読むのは 5 箇所 — `request` / `note_change` / `tick` の
待機への戻し / 静穏時間の判定 / producer の上限。

`job.rs` の起点は子プロセスの起動より前で取る。あとで取ると、子が動き出してから起点が
決まるまでの隙間で上限を過ぎさせられず、上限の検査が決定的に書けない。

これで検査から次の待ちが消えた。

| 検査 | 旧 | 新 |
|---|---|---|
| 静穏時間 | 私有の `State::Pending` を書き換えて過去に倒す | `clock.advance(QUIESCENCE)` |
| producer の上限 | 実時間で 6 秒待つ | `clock.advance(limit)` |
| 引き金の連打 / 起動できない producer | 10ms sleep × 30〜50 周 | sleep なし |
| 編集が続いている間 | 10ms sleep × 20 周 | 静穏時間の半分ずつ進める |

残っている実時間待ちは、子プロセスが実際に動き出したこと (`wait_until`) と、
止めたあと孫が触らなくなったこと (800ms の観測窓) だけ。どちらも注入した時計では
置き換えられない。

`cargo test -p sheaf-core --lib regenerate` の `finished in`: **6.85s → 2.97s** (2 回計測、
それぞれ 6.85/6.90 と 2.97/3.04)。いちばん重い 1 本は孫の停止を見る 2 本で 1.2〜1.3s。

## src/ に残したコメント (なぜ)

実測した外部の癖 — 捨てると知識が消えるもの:

- `store.rs::signature_text` — scip crate の `Signature` は本文が 2 番、rust-analyzer が書く
  旧仕様の `Document` は 5 番。型付きで読むと必ず空文字列になる
- `store.rs::fenced_declaration` — scip-typescript は `signature_documentation` を書かず、
  宣言を ` ```ts ` で括って `documentation` の先頭に入れる
- `store/kind.rs` の冒頭 — 番号は producer の癖ではなく、producer が揃って古い体系を書いている。
  だから表は 1 つでよく、ツール名で分けない
- `store.rs::enclosing_type` / `impl_pair` — derive の impl は定義位置を持たない (37,120 出現中 397)。
  ジェネリックな impl はブロックの符号を持たずメソッドの符号しか出ない
- `store.rs` の `definitions` / `references` / `trait_impls` — scip-typescript は索引ルートの
  情報を含まない座標を振る。実索引の occurrence は 9 万を超える。rust-analyzer は
  `relationships` を出さない
- `store/scip_split.rs` の冒頭 — `Index` 全体をデコードすると 12.4MB が常駐 86.9MB、
  範囲を切るだけなら 17.0MB。`CodedInputStream` は上流が非公開 API と明言している
- `store/scip_split.rs::ColumnEncoding` — Unspecified は「バイトオフセット」ではない。
  scip-go はバイト、scip-typescript は UTF-16 を、どちらも宣言せずに出す
- `store/load.rs` — scip-go はインタフェース埋め込みで自己ループの辺を出す (実索引に 3 件)
- `regenerate.rs` / `job.rs` — producer は起動後もソースを読み続ける (rust-analyzer で 0.6〜1.0 秒)。
  生成 1 本のピークが 2.3GiB なのでロックはリポジトリ単位。空の索引を exit 0 で書く producer がいる
- `regenerate/producer.rs` — 版を固定する理由 (`npx` が解決した typescript の版が符号の綴りに埋まる)、
  `--infer-tsconfig` が対象のツリーに書き込むこと、上限 300 秒の根拠 (74 秒 + cargo のロック待ち)
- `regenerate/provenance.rs` — `require_git(false)` が既定でないこと、mtime も見る理由
- `store/scip_split.rs::document_header` — let-chain を使わないのは rust-version 1.85 のため

設計判断の「なぜ」 — コードが答えていないもの:

- `lib.rs` の `Definition` / `References` / `Implementations` — 確信度を分ける理由と
  `compile_fail` doctest 5 本。**この doctest は不変条件そのものなので消さない**
  (`cargo test -p sheaf-core --doc` で「コンパイルできないこと」を検査している)
- `store.rs::Freshness` — 全か無かにする理由 (残りだけ返すと消えた候補が呼び出し側に見えない)
- `store.rs::references_of_symbol` / `references_in_document` — 0 件の Document が
  鮮度の検査に載らないので、`None` と空を分ける
- `job.rs` — 索引を先に置いて出自を後に書く順の理由、一時ファイルに PID を入れる理由、
  ロックの「ほかが持っている」と「置き場所が無い」を分ける理由
- `store/slot.rs` — 取り出す口をツリーのルート込みにする理由

剥がしたもの: 何をしているかの説明 (`InDocument::definitions` など)、名前で言えている説明、
2〜4 箇所に書かれていた同じ説明 (local 符号の扱いが 4 箇所、私有フィールドと公開 getter で
同じ文が 2 回)、Markdown の装飾 (`**`。plain text として読まれる)。

### 不変条件 (rewrite-plan 4.3 の 1〜5) をどのテストが固定しているか

1. 確信度は variant から逃れられない
   - `compile_fail` doctest (`crates/sheaf-core/src/lib.rs`、tests/ の管轄外) が型として固定
   - 呼び出し側でそれが成り立つことは
     `references.rs::参照の答えは確信度で分かれる` (Exact / Syntactic / NotCode)、
     `describe.rs::実装先の答えは確信度で分かれる` (Exact / Derived / Unknown / NotCode)、
     `definition.rs::索引が答えられない位置は構文層に回る` (`Syntactic(vec![])` ではなく `NotCode`)
2. プロヴェナンスは all-or-nothing
   - `definition.rs::索引が答えられない位置は構文層に回る` (行「飛び先のファイルが変わった」「出自を申告されていないファイル」)
   - `definition.rs::候補の一部だけが古いときは部分的な_exact_を返さない`
   - `definition.rs::別のツリーでは内容が一致したファイルだけ_exact_を返す`
   - `dispatch.rs::経由先の参照が載るファイルが変わったら構文層に回る` (経由先も依拠集合に入る)
   - `enclosing.rs::型に落とせない条件では構文層に回る`
   - `layout.rs::接ぎ木でルート内に入ったdocumentは出自が合わなければexactにしない`
3. Exact と Derived / Enclosing は混ざらない
   - `describe.rs::実装先の答えは確信度で分かれる` (rust-analyzer は `Derived`)
   - `describe.rs::索引が関係を書いていれば実装先はそのまま答えになる` (`relationships` は `Exact`)
   - `enclosing.rs::定義位置を持たない符号は囲んでいる型に落ちる` (`Enclosing`)
   - `enclosing.rs::語そのものの定義があれば型には落とさない` (弱い答えを `Exact` に混ぜない)
4. 名前一致の解決は言語を跨がない (`same_language`)
   - sheaf-core 側には名前一致の層が無い (`SymbolIndex` は conductor 側) ので、
     tests/ には該当する検査が無い。ここは `src/semantic_index/` の管轄
   - 索引をまたいで符号を突き合わせないことは `layout.rs::同じ符号が別の索引にあっても混ざらない` が固定
5. 世代は内容キー
   - `IndexRoot::fold` は conductor 側 (`src/semantic_index/roots.rs`)。tests/ が固定するのは
     その手前、内容ハッシュで鮮度を決める側で、上の 2 と同じテスト群

### 残したコメント (なぜ)

コードから読み取れない「なぜ」と、実測した外部の癖だけを残した。

外部プロデューサの実測 (捨てると知識が消える):
- `describe.rs` `document_signature` — rust-analyzer は `Signature` の本文を旧仕様の 5 番に書く
- `describe.rs` `information` / `番号の意味はツール名に依らない` — 種別の番号は producer をまたいで同じ
- `describe.rs` `実装先の答えは確信度で分かれる` — rust-analyzer は `relationships` を 1 件も書かない
- `describe.rs` `fenced` — scip-typescript は種別も宣言も書かず、doc のコードブロックに入れる
- `definition.rs` `build_shift_index` / `未指定エンコーディングでは…` — 列が UTF-16 単位なのに Document が宣言しない
- `definition.rs` `document_側のエンコーディング宣言を読む` / `utf16_を宣言する索引は投入しない` — 2 つの encoding フィールドの違い
- `dispatch.rs` `自分自身を実装していると名乗る符号は経由先にしない` — scip-go の SRC == DST の辺 (実索引に 3 件)
- `layout.rs` `同じ符号が別の索引にあっても混ざらない` — scip-typescript の `npm . .` 座標
- `layout.rs` `索引ルートが2つあっても…` — 実測対象で go.mod が 8 個、うち 1 つが入れ子
- `go_definition.rs` `ルートを間違えると…` — scip-go は go.mod を見つけられないと空の索引を exit 0 で書く
- `ts_definition.rs` `scip_typescript_は対象のツリーに何も書かない` — `--infer-tsconfig` が書き込む経路
- `memory.rs` — 符号の平均長と件数、実測倍率 (Rust 1.20 / Go 1.35)
- `definition.rs` 実索引の 2 本 — release/debug で 8 倍、出自を歩くと 95ms 対 46ms

設計判断の「なぜ」 (コードが答えていないもの):
- `common/mod.rs` `Rough` — 雑な構文層で通ることが「索引の規則が構文層の賢さに依存していない」の検査になる
- `common/mod.rs` `load_as_indexed_tree` — 実運用の申告元は git / 実索引のツリーは target が数十 GB
- `definition.rs` 冒頭 — 確信度が型として逃れられないことは doctest 側が見ている
- `definition.rs` `索引が答えられない位置は構文層に回る` — Exact の意味 (依拠した全ファイルが生成時のまま)
- `definition.rs` `別のツリーでは…` — 全部落とすと worktree で索引を使い回す意味が無くなる
- `definition.rs` `候補の一部だけが…` — 部分的な Exact は「索引がすべて答えた」と読まれる
- `definition.rs` `ツリーの外を指す…` — 索引ファイルは外から来る入力で `Path::join` は絶対パスにルートを捨てる
- `dispatch.rs` `経由先の参照が…` — 経由先を依拠集合から外すと「無い」と「言えない」が区別できなくなる
- `dispatch.rs` `実リポジトリ_実装関係の辺を…` — 直接参照を持つメソッドを選んである理由
- `enclosing.rs` `型に落とせない条件では…` / `語そのものの定義があれば…` — 弱い答えを混ぜない
- `layout.rs` `パスが衝突したら…` / `接ぎ木でルート内に…` — 誤答が起こり得る唯一の箇所、対照を置いた理由
- `references.rs` — 参照先が 1 つでも違えば件数そのものが信用できない
- `definition.rs` 実索引の 3 本 — 対照を置く理由、Document 先頭のモジュール定義が全体を覆う話

剥がしたもの: 何をしているかの説明、`// ここから先は実索引が要る` のような `#[ignore]`
が既に言っていること、ビルダー化で自明になった fixture の組み立て説明、複数ファイルに
同じ内容が書かれていた `SyntacticLayer` の説明 (common に 1 箇所へ集約)。
