# 実装計画書: 前回のレビューからの進みを出す

- 日付: 2026-08-13
- 起点: PR #319「revidere をベースから作業ツリーまでの全差分でレビューする」から
  切り出した追加分。#319 はレビュー範囲の修正で、こちらは表示の追加。混ぜると
  「画面が変わった」のがどちらの由来か切り分けられなくなるので分けた。
- ステータス: 実装済み (コミット 555d080)。実機確認と PR 作成が残っている。

## 現状

レビューは毎回ゼロベースで作り直す (#319)。これは正しいが、2 度目以降の読者は
「前に読んだときから何が動いたのか」を知る手立てが無く、全部を読み直すことになる。

前回の対象コミットは成果物にしか残っていない。#319 で `head` が解析時の HEAD
コミット ID になったので、初めてここを起点に差分を語れるようになった。

## ゴール

レビュー本体はゼロベースのまま、「前回のレビューから何が動いたか」だけを別に
持たせる。最低限、前回と今回のコミット ID、その間で変わったファイル、履歴が
書き換わったかどうか。

## 非ゴール

- 前回の分類 (節・重要度) の持ち越し。履歴が書き換わったときに、何が根拠だった
  のか誰にも分からなくなる。
- 前回からの差分だけをレビューするモード。読む範囲を狭めるのは別の判断で、
  まず「何が動いたか」が見えてから考える。

## 実装

| 置き場所 | 中身 |
|---|---|
| `crates/revidere/src/review.rs` | `SincePrevious` (previous_head / head / files / history_rewritten) と `Review` の任意フィールド |
| `crates/revidere/src/analyze.rs` | `previous_head()` が上書き前の成果物を読み、`since_previous()` が git から引き直す |
| `crates/revidere/src/git.rs` | `is_ancestor_of_head` と `changed_files` |
| `crates/revidere/src/annotate.rs` | 読み側のアクセサ |
| `src/ui/revidere_view.rs` | `push_since_previous` — 概要の先頭に出す |

版は conductor 0.106.0 / revidere 0.3.1。成果物のスキーマは上げていない
(`serde(default)` の任意フィールドなので、古い成果物もそのまま読める)。

### 決めたこと

- **成果物は上書きする前に読む。** 前回の対象コミットはそこにしか残っていない。
- **スキーマ版が違う成果物は読まない。** `head` の意味は版によって変わりうるので、
  読めた文字列をコミット ID として扱うのは推測になる。
- **`files` は前回の HEAD から「今の作業ツリー」まで。** コミット間ではなく、
  レビューが実際に見ている範囲に合わせた。未追跡ファイルも繋ぐ — 新しく足した
  ファイルが「変わっていない」側に落ちると、一番読みたいものが消える。
- **履歴が書き換わっても止めない。** rebase 直後はオブジェクトが残っていることが
  多く、ファイル一覧は取れる。取れなければ一覧を諦めて、履歴が変わったことだけを
  伝える。画面ではその旨を警告色で断る。

## 分かっている穴

- **`files` は「前回のレビュー以降」ではなく「前回の HEAD 以降」。** 前回の成果物も
  作業ツリーを見ていたので、そのときの未コミットの変更は復元できない。コミットせずに
  2 回続けて解析すると、1 回目と 2 回目の手元の変更の差はここに出ない。
- 前回の HEAD が完全に消えている (gc 済み) と `files` は空になり、
  `history_rewritten` だけが立つ。
- ファイル一覧をそのまま全部出している。数が多いときの省略は入れていない。

## 残っている手順

### T1. 実機で表示を確かめる

このリポジトリ自身で 3 通り見る。ここまでは自動テストが見ていない。

1. 成果物を消してから解析 → 概要にサマリが出ないこと
2. 何かコミットしてもう一度解析 → 前回と今回のコミット ID、変わったファイルが出ること
3. `git commit --amend` してから解析 → 履歴が書き換わった旨の断りが出ること

3 の文面は 2 行に折り返る長さなので、幅を狭めたときの見え方も併せて見る。

### T2. PR を作る

タイトルは「feat: 前回のレビューからの進みを成果物に持たせて画面に出す」。
本文には上の「分かっている穴」を、そのまま制約として書く。
