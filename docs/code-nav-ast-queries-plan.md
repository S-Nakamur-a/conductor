# 実装計画書: コードジャンプのクエリ層を AST に接続する

- 日付: 2026-07-31
- 起点: daisy 壁打ちの結論「LSP には移行しない。tree-sitter を維持し、クエリ側をインデックスの構文情報に接続する」。worktree 切替時は index を作り直す・着手範囲は全部、はユーザ裁定済み。
- ステータス: draft

## ゴール

ユーザの要求は次の 2 点。**この 2 点がスコープの判定基準であり、当てはまらないものは計画に入れない。**

1. **誤判定をなくす** — コメント中の単語に関数ジャンプが付くなど、本来コードでない箇所への誤検出を潰す。
2. **worktree 並列でメモリを大量消費しない** — 精度を上げる代わりに常駐メモリが膨らむ方式（LSP 常駐）を採らない。

解析器は替えない。定義抽出は既に AST ベースで正しく、壊れているのは AST を参照しないクエリ層なので、そこを構文情報に接続する。

> **スコープの経緯（2026-07-31、ユーザ指摘による是正）**: lead が調査中に見つけた項目を計画に足しすぎていた。`gd` がどの行を見るか（旧 S6）は上の 2 点のどちらでもないので取り下げた。**S4（worktree 追従）と S5（候補一覧の表示）も同様に lead が足した項目**で、承認は得ているが当初の 2 目的の外にある。以後、項目を足すときは上の 2 点のどちらに当たるかを明記すること。

## 非ゴール

- LSP（gopls / rust-analyzer / tsserver）への移行。実測でジャンプ可能出現の 80.4% が既に一意、6件以上に化けるのは全 2557 名中 6 名前のみだったため、型解決に投資する根拠がない。
- 呼び出し箇所の型を見ないと絞れない真の多態性（trait デフォルト実装 vs オーバーライド、ジェネリクス経由の型消去）の解消。原理的に型解決が要る範囲で、実測では 6.34%。
- SCIP / LSIF による事前インデックス。将来この残余が効いてきた場合の escalation 先としてのみ記録（常駐 LSP ではなくこちら）。

> **⚠ 非ゴールの根拠に対する留保（接地役の追加実測、2026-07-31）**
>
> 「型解決に投資する根拠がない」という判断は **曖昧さの分布**（ジャンプ可能な出現のうち 80.4% が一意）に基づいていた。しかし `rust-analyzer scip` の実出力を protobuf でパースし、**同一の (file, line, col) 位置**で tree-sitter 索引と突き合わせたところ、本当の差は曖昧さではなく**カバレッジ**だと判明した:
>
> | tree-sitter の定義数 | SCIP が解決 | SCIP も未解決 | 合計 |
> |---|---|---|---|
> | 0件（＝今は飛べない） | 67,890 | 2,981 | 70,871 |
> | 1件 | 25,815 | 0 | 25,815 |
> | 2-5件 | 4,267 | 0 | 4,267 |
> | 6件以上 | 1,999 | 38 | 2,037 |
> | **合計** | **99,971 (97.1%)** | 3,019 | 102,990 |
>
> つまりコード位置の識別子のうち、tree-sitter 索引が一発で解決できるのは **25.1%**、SCIP は **97.1%**。曖昧さ（2件以上）は 6,304 出現＝**6.1% に過ぎない**。
>
> **ただしこの 97.1% を額面通り受け取ってはいけない。** 解決できていない側の上位は `Some` `assert_eq` `None` `String` `Vec` `to_string` `unwrap` `std` といった std/外部クレートの名前と、`viewer_state` `area` `frame` `len` `width` のような**ローカル変数・フィールド・メソッド名**である。ローカル変数へ「定義ジャンプ」しても、レビュー用途での価値は薄い。またフィールドは `index.rs:127` で意図的に除外している。
>
> **この計画への影響はない**（S1〜S6 はすべて解析バックエンドに依存しない修正で、SCIP を将来入れても等しく必要）。ただし SCIP の位置づけは「遠い将来の escalation 先」より高い。実測では **13秒 / ピーク 2.36GB / 成果物 10.6MB、しかもピークは生成時のみで常駐しない**（2回実行して出力バイト数まで決定的）。再評価するなら「多態性の残余が効いてきたら」ではなく「飛べない識別子の多さが不満になったら」が正しいトリガ。
- 複数 worktree 分の index 同時保持。ユーザ裁定で「切替のたびに作り直す」を採用済み。

## 設計判断（ADR）

### D1: マスクは「行内の識別子出現インデックス」で持ち、**index には保存せず開いているファイル 1 本だけ持つ**

- 採用: 「この行の k 番目の識別子出現はコード位置である」という集合を、**`open_file` の時に開いたファイル 1 本ぶんだけ計算して `ViewerState` に持つ**。クエリ側は描画行に同じ正規表現を当てて k を求め、集合に問い合わせる。`find_references` は全ファイルを走査するが、**走査中にその場で計算する**（既に各ファイルを読んでいるので追加の読み込みは発生しない）。
- **`IndexData` は変更しない。**
- 捨てた代替案（当初案）: **全 306 ファイルぶんのマスクを index に保存する** — マスクが必要なのは**今表示しているファイルだけ**で、ユーザは一度に 1 ファイルしか見ない。306 ファイル分を常駐させるのは丸ごと無駄。1 ファイルのパースは実測から ≒ 0.4ms（121ms / 306 ファイル）なので開くたびに計算して足りる。
- 根拠: `file_content` を埋める経路は `src/viewer/content.rs` の `open_file` **1 箇所だけ**で、diff 表示も同じ配列にアノテーションを重ねるだけ（`src/viewer/diff_view.rs`）。したがって `open_file` で計算すれば plain / diff の両方を覆える。**既存の `test_runs`（`src/viewer/content.rs:60`）がまさに同じ形の per-open-file キャッシュで、前例がある。**
- 副次的な利点: マスクは開いているファイルの**実テキスト**（＝選択中 worktree のファイル）から計算されるので、**index のルートが何であれ常に自己整合する**。座標系のズレがこの経路には原理的に入らない。

#### D1-a: 極性は「コード位置の許可リスト」にする（NFR 役の推奨を却下）

- NFR 役の実測: コメント/文字列を含む行は約 **15,500**、コード識別子を含む行は **49,295**。したがって「除外集合を持つ」方が約 **3.2 倍疎**で、メモリ的には有利。
- **それでも許可リスト（コード位置の集合）を採る。** 理由は**失敗の向き**:
  - 許可リストが空になる失敗 → **何もジャンプできなくなる**（機能が死ぬ）
  - 除外リストが空になる失敗 → **全部ジャンプ可能になる**（＝今のバグそのものに戻る、しかも誰も気づかない）

  壁打ちで確定した「誤って飛ぶコストは飛べないコストより高い／検出漏れ側に倒すのが正しい」という判断に、許可リストの失敗の向きが一致する。
- メモリ差が判断に効かない理由: D1 の改訂で**保持するのは開いているファイル 1 本ぶんだけ**になったので、3.2 倍の差は数 KB 対数 KB の話になり、極性の選択は性能問題ではなくなった。NFR 役の数字は「index に全ファイル分を持つ」当初案への評価としては正しく、その前提が消えた。
- **対応外の言語の扱いがこれで決まる**: viewer は Python など grammar を持たない言語のファイルも開ける。許可リストなので、**grammar が無い言語のファイルは丸ごとジャンプ対象外**になる。これは正しい挙動（何がコードか判定する手段が無いのだから）で、しかも現状の隠れたバグを塞ぐ — 今は Python ファイルを開いていても、Rust の索引名と一致する単語に下線が引かれてしまう。
- 捨てた代替案:
  - **ソースのバイト範囲を持ち、クエリ時に桁変換する** — `file_content` はタブ展開済み（`src/viewer/content.rs:47-49`）で、Go は gofmt でタブが標準。描画時にソース行を持っていないので逆変換できない。
  - **描画桁で持つ** — `tab_width` は実行時 config（`config.viewer.tab_width`）なので index 構築時に未知。
  - **ソース行も index にキャッシュする** — ファイル全体を二重保持することになる。
- 根拠: タブ展開は `\t` を空白 N 個に置換するだけで、識別子の**順序もテキストも変えない**。よって「行内 k 番目の識別子」は展開前後で不変。
- 撤回条件: index 側とクエリ側で識別子の正規表現が食い違うと破綻する → **同一の正規表現を 1 箇所に定義して両者が使う**ことを S1 の契約とする。これが守れない設計になったら D1 は撤回。
- 起点: lead 起草（Phase 0 でタブ展開を発見して設計変更）

### D2: TS は `string_fragment` をマスクし、`template_string` / `template_substitution` はマスクしない

- 採用: 文法ごとに明示的なノード種別の許可リストを持つ。

  | 文法 | マスクするノード |
  |---|---|
  | Rust | `line_comment` `block_comment` `doc_comment` `string_content` `raw_string_literal` `char_literal` |
  | Go | `comment` `interpreted_string_literal_content` `raw_string_literal_content` |
  | TS/JS | `comment` `string_fragment` |

- 捨てた代替案: **`"comment" in type \|\| "string" in type` の部分文字列判定** — Phase 0 の実測で `template_string` の子が `['`', string_fragment, template_substitution, string_fragment, '`']` と判明。`template_string` ごとマスクすると `${realCode}` の中の生きたコードまで潰れる（＝検出漏れ）。TS は `string_fragment` だけ掴めば通常文字列とテンプレートの文字部分の両方を覆い、補間部は自然に残る。
- 起点: lead 起草（Phase 0 で 3 文法を実測）

### D3: シグネチャは index に持たず、候補一覧を開くときにファイルから抽出する

- 採用: `hover_info::extract_signature` を再利用し、一覧生成時に定義ファイルを読む。**所属型（owner）だけ**は AST の親を辿らないと取れないので index に持つ。
- 捨てた代替案: **構築時に全定義のシグネチャを保持する** — 2815 定義分の文字列を常時抱えることになるのに、使われるのは一覧を開いた瞬間だけ。一覧は最大でも数十件なので on-demand の読み込みで足りる。
- 撤回条件: 一覧を開く体感が目に見えて遅くなったら index 側に寄せる。

### D4: worktree 切替時は index を無効化してから再構築する（世代カウンタ付き）

- 採用: 切替で `available = false` にし、世代カウンタを進めてから再構築する。ビルド完了時、自分の世代が最新でなければ結果を捨てる。
- 捨てた代替案:
  - **無効化せず再構築だけする** — 再構築中は古い index が生きているので、まさに今回直そうとしている「別ブランチの行番号に飛ぶ」が再構築完了までの間だけ残る。
  - **複数 worktree 分を同時保持** — ユーザ裁定で不採用。
- 根拠: `src/background.rs:24-31` の `BackgroundOp::start` は receiver を差し替えるだけで古いスレッドは走り続け、`src/symbol_index/index.rs:115-118` で共有の `Arc<Mutex<IndexData>>` に書き込む。ルートが変わる設計では旧ルートのビルドが新ルートの結果を上書きし得る。
- 撤回条件: 再構築が debug ビルドで 300ms を超え体感されるなら、「切替のたびに作り直す」自体をユーザに差し戻す（選択中＋直前の 2 本キャッシュ案が控え）。
- 起点: ユーザ裁定（作り直す方式）＋ lead 起草（世代カウンタは Phase 0 の接地で追加）

### D5: 既存の `on_worktree_changed()` に一本足す + 初期化系を別系統にする（2系統）

- 採用: **`src/app/worktree.rs:59` の `on_worktree_changed()` に index の再ルート＋再構築を足す**。加えて初期化系（`view_state.rs:47` の復元完了時 / `main.rs:254` の初回）で 1 回だけ起動する。
- 捨てた代替案: **`selected_worktree` への代入 13 箇所を機械的に 1 メソッドへ置換する**（当初案）— **接地で誤りと判明。以下の箇所で壊れる**:

  | 箇所 | なぜ触ってはいけないか |
  |---|---|
  | `app/repo.rs:191` | `refresh_worktrees` 内。**3 秒ごとのポーリング**で走るので、通常時に毎 3 秒 208ms のビルドが積み上がる |
  | `app/mod.rs:527` `sync_selected_worktree` | **マウスホイールのたび**に走る（`event/mouse/scroll.rs:51,55`）。呼び出し側の `prev_wt != selected_worktree` ガードに依存しており、ここ自体に足すとホイール操作でビルドが積み上がる |
  | `app/worktree_crud.rs:329` | 新規 worktree に**一時的に**選択を移して Claude Code を spawn するための退避。コメント（326-327 行）に「`on_worktree_changed()` が 🌱 バッジを消すのを避けるため意図的に直接代入」と明記されている |
  | `event/mouse/bars.rs:106` | 削除ボタンのクリック。`ConfirmingDelete` に入るために選択を動かすだけで、切替ではない |
  | `app/repo.rs:45,104` | リポジトリ切替直後の 0 での仮置き。直後に `restore_selected_worktree_and_view()` が本来の選択で上書きするので、誰にも観測されない中間値。ここで仕掛けると必ず 1 回無駄になる |

- 根拠: `on_worktree_changed()` の既存の中身（`worktree.rs:59-115`）は「reflow を閉じる / editor を破棄 / viewer_state をリセット / current_view_branch を差し替え / DB に選択を保存」＝**ワークツリー境界の切り替え処理そのもの**なので、index の再ルートを足す場所として意味論が一致する。
- 撤回条件: `on_worktree_changed()` を呼ばない切替経路が新たに見つかったら、その経路にも足す（＝funnel の前提が崩れる）。
- 起点: lead 起草 → **接地役の FAIL により全面改訂**

### D6: 世代カウンタは `SymbolIndex` 側に置く（`BackgroundOp` では止められない）

- 採用: `SymbolIndex` に世代番号を持ち、ビルド開始時に採番、結果書き込み前に最新世代かを検査して古ければ破棄する。
- 根拠（接地で実証済み）: `src/background.rs:28-30` の `BackgroundOp::start` は新チャンネルを作って `self.rx` を差し替え、`JoinHandle` を捨てる。**古いスレッドは止まらず `tx.send` が `Err` になるだけ**で、`send` は `index.build()` の後（`src/app/code_nav.rs:636-640`）なので、**共有 `Arc<Mutex<IndexData>>` への書き込み（`index.rs:115-118`）はチャンネルが切れていても必ず実行される**。`clear()`（`background.rs:81-83`）も受信側を捨てるだけ。つまり `BackgroundOp` を無改造で使う限り、古いビルドを止める手段は存在しない。
- 実証: 提案設計の最小形（`set_root`）を入れて遅いビルド A と速いビルド B を重ねたところ、**root は B を指しているのに index の中身は A** になる競合を再現した。窓の大きさは build 全体 ≒ 208ms で、j/k 連打や strip のクリック連打で十分届く。
- 注記: **この競合は「現状のバグ」ではない。** 現状 `root` に setter は存在せず（`index.rs` の `root` 書き込みは `new()` のみ）、index はリポジトリルートに固定されている。**再ルート設計を入れることで新規に生まれるリスク**なので、設計と同時に塞ぐ。
- 捨てた代替案: `BackgroundOp` にキャンセル機構を足す — 影響範囲が index 以外の全バックグラウンド処理に及ぶ。世代検査は index 内で完結する。

## 実装ステップ

縦切り。S1 で「index にマスクを持たせ、クエリ 1 地点がそれを参照する」最薄の経路を通し、テスト化可能な受け入れ条件の failing test をここで実行可能にする。

### S1: マスクのデータモデルと、symbol hint への接続（walking skeleton）
- **判定器**: 新規テスト `symbol_index::tests::masks_comments_and_strings_per_language`（Rust / Go / TS のフィクスチャで、コメント・文字列内の識別子出現インデックスが除外され、TS の `${...}` 内は除外されないことを assert）＋ `app::code_nav::tests::hints_skip_comment_words`。`cargo test` 緑。
- 担当: **lead 直書き**（判定器は書けるが、このステップ自体がデータモデルと共有正規表現の設計＝ D1 の契約を確定させる。spec を書き切ると実装とほぼ同義になるため、委譲は lossy なだけで利得がない）
- 触るファイル: `src/symbol_index/`（マスク計算を公開する新モジュール）、`src/viewer/content.rs`（`open_file` で計算）、`src/viewer/state.rs`（保持場所）、`src/app/code_nav.rs`（参照）

## 敵対的精読（6-0）で見つかった欠陥と対応

lead が「不安だ」と名指しした 6 点（`from_masked_ranges` のカーソル、手書きの tree-sitter 走査 2 本、世代カウンタのデッドロック、遅延パースの境界、タブ展開の前提、128 上限）は**全部シロ**だった。307 ファイル + 4 万本の変異入力を総当たり参照実装と突き合わせて不一致ゼロ。壊れていたのは**周辺の配線**で、5 件。

1. **【lead が入れた回帰】Rust の inline format 引数 945 箇所が潰れた** — `println!("{widget:?}")` の `widget` が散文として masked に。**TypeScript の `${...}` は D2 で明示的に手当てしたのに、Rust の等価な構文だけ漏れていた**という非対称。tree-sitter-rust は format 文字列を分割せず `string_content` 1 個で寄越すので、文法では解けずマスク範囲の後処理が要る。→ `subtract_format_args` を追加し、`{ident}` / `{ident:spec}` の識別子部分をマスクから差し引く。`{{` は escape、`{}` `{0}` は識別子なしとして対象外。**実測 954 箇所中 950 箇所が復帰**（残り 4 は `'\u{a0}'` の char escape とテスト自身のフィクスチャで、いずれも正しい挙動）。
2. **【lead が入れた回帰】ホバー 1 回で 100〜157ms の UI フリーズ** — `hover_info.rs` が毎ホバー同期で `find_references` を呼び、マスクのため該当ファイルを全部パースしていた。実測 `App` 2.4→100.6ms、`new` 2.2→157.2ms（197 ファイル）。16ms/frame なので 6〜10 フレーム落ち。→ `count_references_upto(name, root, cap)` を追加し、ホバーは 50 件で打ち切って `50+` と表示する。**ポップアップの参照数は装飾であって正確さを要求しない**という判断。
   - **判定器自身が安心を与えていた**: レイテンシゲートが検索名に `find_references`（6 ファイルしか当たらない最良ケース）を使っており、ヒット数に線形なコストを測れていなかった。`new`（最悪ケース）で capped 経路を測る `hover_reference_count_stays_within_a_frame` に差し替え、uncapped 側は別テストに分離。
3. **リポジトリ切替で index が古いリポジトリを指したまま** — `switch_repo` が `start_symbol_index_build()` を呼ばない。**lead は「起動・worktree 切替・fs 変更を 1 箇所に集めた」とコメントに書いたが、リポジトリ切替が列挙から漏れていた唯一の root ドリフト経路。** 相対パスは両リポジトリに存在しがちなので、新リポジトリのファイルを旧リポジトリの行番号で開き、ホバーは旧リポジトリのソースを読む。→ `restore_selected_worktree_and_view()` の直後に 1 行追加。
4. **worktree 一覧をホイールで流すとフルリビルドが積み上がる** — `on_worktree_changed` は選択が変わるたびに走るので、10 個流せば 10 本の並行フルツリーパース。その間ずっと `available=false` でナビゲーションが死ぬ。**接地役がこのリスクを警告し、lead は S4 の検証項目に入れたのに実施しなかった。** さらに `app/worktree.rs` の根拠コメントが「ホイール経路は `on_worktree_changed` を呼ばない」と書いていたが事実と逆だった。→ fs 経路と同じ `is_running()` ガードを追加。
   - **ただしガードだけでは index が永久に空になる**（走行中のビルドは世代不一致で結果を捨て、後続が起動しない）。`update.rs` のビルド完了ハンドラに「まだ available でなければ追いかけビルドを起動」を追加して閉じた。
5. **`root` と `generation` を不可分に読んでいない**（未再現・構造としては実在） — 2 つのロック取得の間に `set_root` が入ると、古い木を歩きながら新しい世代を刻印して publish が通る。**世代カウンタが防ぐはずのものそのもの。** → root のロックを保持したまま generation を読む形に変更。`set_root` と同じロック順なのでデッドロックしない。

- **D1-a を追加（NFR 役の推奨を却下する裁定）**: 極性は許可リスト（コード位置の集合）。NFR 役は実測（コメント/文字列行 15,500 vs コード識別子行 49,295）から除外リスト側が 3.2 倍疎で有利と推奨したが、**メモリ差は D1 改訂で無意味になり（1 ファイル分しか持たない）、失敗の向きで決めるべき問題に変わった**。許可リストなら失敗時に「飛べない」、除外リストなら失敗時に「全部飛べる＝今のバグに戻る」。壁打ちの「検出漏れ側に倒す」判断に前者が一致する。
- **S3 に遅延パースを追加（lead が発見）**: NFR 役の build 予算の議論を追う過程で、`find_references` に素直にマスクを足すと **8〜10ms → 130〜200ms** の性能回帰になることに気づいた。regex でヒットしたファイルだけをパースする形にし、判定器に 30ms のレイテンシゲートを入れた。
- **S1 に `walk_tree` のカーソル使い回しを追加（NFR 役の実測）**: `extract_common.rs:15` が再帰の各ノードで `node.walk()` を呼び `TreeCursor` を毎回ヒープ確保していた。使い回しで抽出 76→53ms、build 全体 216→191ms。既存の無駄で、S1 がどのみち触るファイル。

## 実装役が自分で決めた点（spec の穴）

- **S2: 呼び出し箇所が指示と違う場所にあった** — spec は「hover と Cmd+Click は両方 `event/mouse/viewer_panel.rs`」としたが、実際は Cmd+Click のみそこで、hover 下線と auto-hover は `event/mouse/mod.rs` の `handle_mouse_event` 内だった。実在する 3 箇所すべてにゲートを掛けた。→ **lead 裁定: 追認。** spec の調査不足で、実装側の発見が正しい。
- **S2: `masked_symbol_at_column` という純粋関数に集約した** — 呼び出し側が `&mut App` を触るイベントハンドラでユニットテストしづらいため、既存の `underline_color_kind` / `popup_highlight_range` と同じ「純粋関数を切り出してテストする」パターンに揃えた。→ **lead 裁定: 追認。** 既存の慣習に沿っており判定器も満たしやすい。
- **S3: grammar の無い言語で `find_references` が常に 0 件になる** — spec が「ヒットのあったファイルは `CodeMask::compute` を呼んでコード位置かを判定する」としか書いておらず、grammar 未対応言語（`.py` `.c` `.java` 等）の扱いを決めていなかった。素直に実装すると空マスク＝全部非コード扱いになり、**その言語では参照検索が常に 0 件を返す**。実装役はこれを実装したうえで副作用として報告し、代替案（マスク無しで regex ヒットをそのまま採用）を推奨した。
  → **lead 裁定: 差し戻して修正。** 実装役の推奨どおりに直した。**理由**: D1-a の「失敗は『飛べない』側に倒す」という判断は**ジャンプの提示**についてのもので、検索結果には当てはまらない。ジャンプは 1 語についての主張なので黙るのが安全側だが、**参照検索はリポジトリ全体についての主張**で、「0 件」は沈黙ではなく「存在しない」という断定になる。判定できないだけなのに 0 件と答えるのは、まさに今回潰そうとしているサイレントな誤情報そのもの。一覧に混じったコメントヒットは目に見えて捨てられるが、消えた一覧は気づけない。
  → `CodeMask` に `is_supported()` を追加し、「解析できなかった」と「コードが 1 つも無い」を区別できるようにした（両者はビット列だけでは同一で、扱いが逆になる）。回帰テスト `find_references_keeps_hits_in_unparseable_languages` を追加。

- **S2: `#[derive(Debug)]` の扱いが変わった** — 行頭プレフィックス判定を撤去したので、属性行が `Some("derive")` を返すようになった（旧実装は行頭 `#` を機械的に除外していた）。実装役が副作用として報告。
  → **lead 裁定: 追認。** 属性はプロースではなく実コードなので、マスクがコード位置と判定するのは意味的に正しい。旧実装の `#` 除外は鈍器で、**属性の中の本物のシンボル参照まで潰していた** — `#[derive(Serialize)]` の `Serialize` や `#[serde(with = "MyModule")]` は実在の参照で、そこから定義に飛べる方が正しい。索引に無い名前は後段で静かに未定義になるだけ。

## lead 自身が計画から外れた点

- **S4 のテストが最初は成立していなかった。** 「再ルート前に始まったビルドは捨てられる」を、index のハンドルを clone してから `set_root` → `build()` の順で呼ぶことで表現しようとしたが、`build()` は**開始時に**世代を読むので、後から呼べば新しい世代を読んでしまい素通りする。テストが実装ではなく自分の想定を検証していた。
  → 破棄判定を `publish(symbols, generation)` として切り出し、「世代を採番 → 再ルート → 採番済み世代で publish」の 3 手で決定的に検証できるようにした。スレッドを競争させて順序を祈る形は採らなかった。
