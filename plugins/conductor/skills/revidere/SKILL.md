# revidere

変更を節に分け、各節に重要度と懸念を付け、全ての変更行がちょうど 1 つの節に属することを目指したレビューを作る。
属しているかはスクリプトが検査し、直しきれなかった漏れはページに出る。
最後に、差分の抜粋と GitHub へのリンクを載せたページを Artifact で出す。

$ARGUMENTS

引数にベース (`origin/main` など) があれば、手順 1 で `--base` に渡す。

## 手順

スクリプトは `python3 "${CLAUDE_SKILL_DIR}/scripts/revidere.py"` で走らせる (以下 `revidere.py`)。
標準ライブラリだけで動き、conductor は要らない。スクリプトは利用者の index や作業ツリーに何も書かない。
自分で差分を読むときも、index を書き戻す `git diff` ではなく `git diff-index -p -M` を使う。

1. **台帳を作る。** `revidere.py prepare [--base <ref>]` をリポジトリの中で走らせる。
   1 行目に作業 dir (毎回 `$TMPDIR` の下に新しく作られる) が、続いて範囲と**変更位置の台帳**が出る。
   exit 2 はベースが決められない等の失敗、exit 3 は差分が無い。どちらも出た文をそのまま利用者に伝えて終える。
2. **読む。** 出た範囲のとおり `git diff-index -p -M <base>` を自分で走らせ、変更されたファイルと、必要なら
   呼び出し元・呼び出し先まで読む。未追跡ファイルはこの差分に出ないが台帳には載っているので、
   台帳にあって差分に出ないパスは新規追加として中身を読む。段階 3 は変更されたコードだけでは書けない。
3. **書く。** 下の「レビューの規則」に従った JSON を `<作業dir>/review.json` に書く。
4. **検査する。** `revidere.py check <作業dir>`。exit 0 なら次へ。
   - exit 1 (説明もれ): 出た位置を既存の節に足すか新しい節を作り、既に分類できている位置の割り当ては
     変えずに、**全体を** `<作業dir>/review.retry.json` に書いて `revidere.py check <作業dir> --retry`。
     直した答えは説明もれが減ったときだけ採られる。直しは 1 回だけ。残っても次へ進む (ページに残りが出る)。
   - exit 2 (読めない・欄が欠けている): 名指しされた欄を直して review.json を書き直し、もう一度 check。
     2 回直しても通らなければ、出た文を利用者に伝えて終える。
5. **ページにする。** `revidere.py render <作業dir>` が `<作業dir>/review.html` を書いてパスを出す。
6. **出す。** ページには**変更したコードの抜粋がそのまま載る**。そのことを利用者に 1 行で伝えてから、
   Artifact ツールで review.html を publish し、リンクを返す。Artifact ツールが無いセッションなら、
   使えないと伝えて review.html のパスを返す。

コードへのリンクは、`origin` が GitHub で、指す側のコミットが `origin` に push 済みのときだけ付く。
未コミットの変更や未 push のコミットはリンクの代わりに理由が出る。抜粋はページの中にあるので読める。

## レビューの規則

読む人が次の 3 段階でレビューを進められるように、変更を整理する。

### 段階 1 — 抽象で掴む

毎回同じ 5 欄を同じ順で埋める。PR description ではなく、読む側の型。

- problem — 何が不足・破綻していたか。新機能なら「〜を足したい」もここ
- change — 追加・変更した責務を 1〜2 文。関数名の列挙ではなく責務で書く
- mechanism — 既存の何と新規の何が、どう繋がって動くか
- placement — なぜそのディレクトリ・型なのか。他の候補を退けた理由があれば書く
- scope — ファイル数と、実際に読むべき数

### 段階 2 — 節ごとに diff を眺める

変更をファイル順ではなく節順にまとめ、各節に重要度を付ける。重要度は 2 段で決める。

1 問目 — この節は、この変更の主目的そのものか、主目的の帰結か。

- 主目的そのもの → core
- テスト・版番号・コメントのみで、本体でない → minor

2 問目 — 帰結だったときだけ聞く。その帰結で振る舞いが変わったか。

- 変わった → ripple
- 変わらない → follow

主目的は 1 つとは限らない。同じ変更に相乗りした独立の変更も core でよい。
「振る舞いが変わったか」は帰結の中を割るためだけの問いなので、主目的の実装が振る舞いを
変えていても ripple にはしない。それは core。

ripple と follow の境目が、この仕事で一番効く。「引数が 1 つ減っただけ」に見える変更が、
実は渡す値そのものや開く対象を別物に変えている、という場合を必ず疑うこと。呼び出し側の
シグネチャが変わっても渡す値と結果が同じなら follow、結果が変わるなら ripple。
ripple を follow に落とすと読み飛ばされる。

同じ段階で、各節に「他の節との関係」も付ける。relations に書き、相手は title で指す。
読む人は中核を 1 つ読んだあと、それを検証しているテスト、それに追従した呼び出し側、
それを説明したドキュメントへ、すぐ移りたいから。

関係は、片方が他方の理由になっている向きで書く。テストは実装を検証しているので、テスト側から
実装側へ向けて書く。ripple と follow は中核の帰結なので、帰結の側から中核へ向けて書く。
逆向きには書かない。

同じ段階で、各節の懸念・指摘を concerns に 1 件 1 文で書く。core の節は concerns が空なら LGTM、
あれば「懸念あり」の札が付き、ページ冒頭の判定に全節の concerns が集まる。だから core の節は
必ず「この中身で通してよいか」を判断してから concerns を決める。core 以外の節も、懸念があれば書く。
何を確かめれば晴れるかまで書けると、読む人がそのまま動ける。

1 つの節が複数の相手と関係することはある (結合テストが中核 2 つをまとめて検証している、など)。
そのときは全部書いた上で、**最も強い 1 本だけ** primary を true にする。primary は 1 つの節につき
高々 1 つ。関係が無い節は relations を空にする。無理に繋がない。

### 段階 3 — 機能への影響

関数ではなく機能の単位で書く。利用者が認識している呼び方を使う。

- 「open_file の呼び出し元が 14 箇所」は書かない
- 「ファイル検索の対象範囲が変わる」を書く

呼び出し箇所の件数やカバレッジの数字は求めていない。既存の実装が変更されたなら、それを使って
いる機能がどう変わるかを書く。変更で直る不都合だけでなく、その選択と引き換えに新しく生まれる
不都合も書く。

### review.json の形

```json
{
  "overview": {
    "problem": "", "change": "", "mechanism": "", "placement": "", "scope": ""
  },
  "sections": [
    {
      "title": "一行の見出し",
      "body": "この節で何が起きているかの説明。マークダウン可",
      "importance": "core | ripple | follow | minor のどれか",
      "reason": "なぜその重要度なのか。どの重要度でも必須",
      "concerns": ["懸念・指摘を 1 件 1 文で。無ければ空配列か省略"],
      "relations": [
        {"to": "相手の節の title をそのまま", "reason": "なぜそう言えるのか", "primary": true}
      ],
      "ranges": [
        {"path": "リポジトリ相対のパス", "side": "new | old | file のどれか", "start": 1, "end": 3}
      ]
    }
  ],
  "impacts": [
    {
      "feature": "機能の名前",
      "change": "何がどう変わるか",
      "verify": "何を確かめれば分かるか",
      "gap": "残る穴。無ければ省略",
      "confidence": "fact | guess のどちらか"
    }
  ]
}
```

ranges の決まり:

- side が "new" なら追加行の後像行番号、"old" なら削除行の前像行番号。start と end は 1 始まりで
  両端を含む。1 行なら end を省いてよい。
- 行を持たない変更 (バイナリ、モードのみ、純粋な rename、空ファイル) は side を "file" にして
  start と end を省く。
- 改名して中身も変えたファイルは、old の行も**新しいパス**で指す。台帳がそう数えている。
- 台帳に載っている位置だけを指すこと。文脈行 (変更されていない行) は指さない。

### 守ること

- 台帳のどの位置も、ちょうど 1 つの節に属すること。どの節にも入らない位置があってはいけないし、
  2 つの節が同じ位置を取り合ってもいけない。これは check が機械的に検査する。
- どの節にも reason を必ず書く。確かめた事実として書くこと。
  follow なら「なぜ振る舞いが変わらないと言えるのか」
  (例:「呼び出し側が渡していた値と、新しく使われる値が同一だから」)。そう書けないなら follow ではない。
  ripple なら「どの帰結として起きていて、振る舞いが何から何に変わったのか」。
  そう書けないなら ripple ではない。
- 重要度を上に倒しておけば安全、ということはない。振る舞いの変わらない帰結を ripple に混ぜると、
  本当に見逃せない帰結が薄まって読み飛ばされる。follow は「読まなくてよい」と言い切るための札で、
  使わないでいると読む量が減らない。実際に不変なものは follow にすること。
- core も同じ。重要そうだからではなく、主目的そのものかどうかだけで決める。帰結を core に上げると、
  この変更が何をしたのかが読めなくなる。
- テストとドキュメントの変更を 1 つの節にまとめない。検証している相手・説明している相手が別なら、
  別の節に分ける。まとめてしまうと、ある中核から「その中核のテスト」へ移れなくなる。
  逆に、本当に 1 つの相手しか見ていないなら分ける必要はない。
- 読んでいない・確かめていない節の concerns を空にしない。確かめられなかったなら、そのこと自体を
  concerns に書く。逆に、好みの言い換えや
  確かめていない「〜かもしれない」で concerns を埋めない。LGTM が読まれなくなる。
- relations の to は、この回答に実在する節の title をそのまま書く。言い換えたり要約したりしない。
- confidence が "fact" なのは、コードの構造から確定していることだけ。読んで書いた予想は "guess"。
  迷ったら "guess"。
- 分からないことを埋めない。確認できなかったなら、その旨を書く。
- 振る舞いの根拠はコード。コメントやドキュメントの主張がコードと食い違っていたら、コードを採った
  うえで、食い違いそのものを節に書く。読む人にとってはそれが直すべき点だから、黙ってコード側で
  上書きしない。ただし「なぜこの置き方なのか」「何を退けたのか」といった意図は、コードには
  書けずコメントや計画書にしか無いことが多い。そちらは出典として使ってよい。
- 日本語で書く。

文章の口調は、このセッションの口調のままでよい。ただし口調が変わっても、上の事実の確かめ方は
一切ゆるまない。確かめていないことを勢いで書いてよいという意味ではないし、分からないことを
埋めてよくもならない。JSON の形・キー・enum の値は変えない。
