# Self Review

現在のブランチの変更（diff）を自分でレビューし、人間のレビュアーが本当に確認すべき箇所だけに
Conductor のインラインコメント（`mcp__conductor__create_comment`）を付ける。

$ARGUMENTS

## スコープ判定

- `$ARGUMENTS` が空 → ブランチ全体の diff（ベースブランチとの差分）をレビュー
- `$ARGUMENTS` がファイルパス（例 `src/app.rs`）→ そのファイルの diff のみをレビュー

## 手順

### 1. diff を取得

ベースブランチを自動判定する（`main` が無ければ `master`）。git コマンドは **1 回ずつ** 実行する。

- `git merge-base HEAD main` でベースのコミットを求める
- `git diff <merge-base>...HEAD` でコミット済みの変更を取得
- `git diff` / `git diff --staged` で未コミットの変更も取得し、ワークツリーの現状を把握する

ファイル指定がある場合は対象ファイルにスコープを絞る。

### 2. 変更サマリ（全体像）を書く

diff 全体を把握したら、まず `mcp__conductor__set_change_summary` で
**「この変更で何をしたいのか」「なぜこれらのファイルを触っているのか」** という全体像を 1 つ書く。
これは PR description に相当し、diff の上部に固定バナーとして表示される。

```
mcp__conductor__set_change_summary:
  body: |
    <変更の目的（何をなぜ）>
    <主要な変更点と、各ファイル群を触っている理由>
    <レビュアーに先に知っておいてほしい前提・スコープ外のこと>
```

- 行アンカーのコメントでは表現できない「文脈」をここに集約する
- 再実行すると上書きされる（常に最新の全体像 1 つを保つ）
- 個別の行への指摘は次のステップのインラインコメントに回す

### 3. 変更行の現在の行番号を確定する

コメントは **新しい側（現在のファイル）の 1-based 行番号** に紐づく。
diff のハンク見出し `@@ -a,b +c,d @@` の `+c` が新ファイル側の開始行。
ただしハンク見出しの計算ミスは表示崩れに直結するため、コメントを付ける箇所は
必ず Read ツールで該当ファイルを開き、**実際の行番号を目視で確認**してから使う。

### 4. レビュー観点で要注意箇所を特定

diff の中から、**人間のレビュアーが本当に見るべき箇所だけ**を拾う：

- **トリッキーなロジック** — 一見して意図が読み取れない条件分岐・アルゴリズム
- **意図的なトレードオフ** — パフォーマンス/単純さ/互換性のために敢えて選んだ実装
- **自信のない箇所** — エッジケースの扱い、並行性、エラーパスで見落としがありそうな所
- **設計判断** — なぜ別の素直な方法を採らなかったか説明が要る所
- **後方互換 / 破壊的変更** — 公開 API・スキーマ・設定の変更
- **セキュリティ/入力検証** — 外部入力・信頼境界をまたぐ箇所

diff を読めば自明な変更（リネーム、定型的な追加、フォーマット、import 整理など）には
**コメントを付けない**。

### 5. セルフコメントを付ける

特定した箇所ごとに `mcp__conductor__create_comment` を使う。

```
mcp__conductor__create_comment:
  file_path: <対象ファイルの相対パス（例 src/app.rs）>
  line_start: <新ファイル側の開始行番号>
  line_end: <終了行番号（単一行なら省略）>
  body: <コメント本文>
  kind: "suggest"  # 観察・トレードオフの指摘。人間に判断を仰ぎたい時は "question"
```

#### コメント作成のガイドライン

- **高シグナル・低頻度** — 「なんとなく」では付けない。1 PR で数件に収める意識
- **「なぜ」を書く** — 何をしたかではなく、なぜそうしたか / どこが不安かを書く
- **`suggest` と `question` を使い分ける** — 観察・トレードオフは `suggest`、人間の回答が欲しい時は `question`
- **日本語で簡潔に** — 1〜3 文
- **絶対パス・`./` プレフィックスは使わない** — リポジトリ相対パスで指定する

良い例:
- `(suggest) ここは O(n²) だが対象は常に十数件なので素直さを優先した。スケールするなら要再考`
- `(question) detached HEAD のケースはこの経路で本当に到達しないと言い切れる？`

悪い例:
- `関数を追加した`（自明）
- `Vec を初期化`（コードを読めばわかる）

### 6. サマリーを報告

```
## Self Review 完了

### 付けたコメント
| 行 | kind | 要約 |
|----|------|------|
| src/app.rs:128-135 | suggest | キャッシュ無効化のトレードオフ |
| src/event.rs:42 | question | エッジケースの到達可能性 |

合計: N 件
```

要注意箇所が無ければコメントは付けず、「レビューしたが、人間の確認が必要な箇所は見つからなかった」と報告する。

## 重要

- コメントはコードファイルに直接書き込むのではなく、**Conductor の code comment 機能**（`mcp__conductor__create_comment`）で付ける
- 付けたコメントは Conductor の Viewer / diff ビューにインライン表示され、`/address-conductor-comment` で対応できる
- 独立した箇所のコメント追加は並列実行してよい
