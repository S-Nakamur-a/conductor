# monstrare

変更を主題に分け、主題ごとに「その変更の仕組みが一目で分かる図」を描いたページを作る。
読む人は全ての diff を読まなくても、何がどう繋がって動くようになったかを掴める。
全ての変更行を説明する検査は revidere の役目で、ここではしない。代わりに、変更したファイルが
1 つ残らずどれかの主題に入っていることだけをスクリプトが検査する。

$ARGUMENTS

引数にベース (`origin/main` など) があれば、手順 1 で `--base` に渡す。

## 手順

スクリプトは `python3 "${CLAUDE_SKILL_DIR}/scripts/monstrare.py"` で走らせる (以下 `monstrare.py`)。
同じプラグインの revidere のスクリプトを借りて動くので、revidere の dir も要る。
スクリプトは利用者の index や作業ツリーに何も書かない。自分で差分を読むときも `git diff-index -p -M` を使う。

1. **一覧を作る。** `monstrare.py prepare [--base <ref>]` をリポジトリの中で走らせる。
   1 行目に作業 dir (毎回 `$TMPDIR` の下に新しく作られる) が、続いて範囲と変更ファイルの一覧が出る。
   exit 2 はベースが決められない等の失敗、exit 3 は差分が無い。どちらも出た文をそのまま利用者に伝えて終える。
2. **読む。** 今のブランチ以外を読むときは `git worktree add` で作業コピーを作らない。作業ツリーが clean なら
   `git switch` で切り替えて回し、終わったら戻す。出た範囲のとおり `git diff-index -p -M <base>` を走らせ、
   変更されたファイルと、図にする流れの呼び出し元・呼び出し先まで読む。一覧にあって差分に出ないパスは
   未追跡の新規ファイルなので中身を読む。図は「どこから呼ばれ、どこへ渡るか」まで読まないと描けない。
3. **書く。** 下の「主題と図の規則」に従った JSON を `<作業dir>/story.json` に書く。
4. **検査する。** `monstrare.py check <作業dir>`。
   - exit 0 なら次へ。
   - exit 1 は、どの主題にも入っていないファイルがある。出たファイルを、扱っている主題の files に足すか、
     新しい主題を作って story.json を直し、もう一度 check。2 回直しても残るなら次へ進む (ページに残りが出る)。
   - exit 2 は story.json が読めないか、欄が欠けているか、指したパスや行が差分に無い。名指しされた所を直して
     もう一度 check。2 回直しても通らなければ、出た文を利用者に伝えて終える。
5. **ページにする。** `monstrare.py render <作業dir>` が `<作業dir>/story.html` を書いてパスを出す。
   render も story.json を検査し直すので、手順 6 で直したあとも check を経ずに render してよい。
6. **見る。** ブラウザを操作できるツールがこのセッションにあれば、story.html を開いてページ全体を 1 枚だけ撮る
   (file: を開けないツールなら、作業 dir で `python3 -m http.server --bind 127.0.0.1` を裏で起こして開き、撮ったら止める。
   `--bind` を外すと、未コミットの変更を含む diff が LAN から読める)。
   図の文字のはみ出し・重なり・消えた文字を 1 回だけ直して render し直す。撮り直しはしない。ツールが無ければ飛ばす。
7. **出す。** ページには**変更したコードの抜粋がそのまま載る**。そのことを利用者に 1 行で伝えてから、
   Artifact ツールで story.html を publish し、リンクを返す。ツールが作業 dir のファイルを読めないと断ったら、
   このセッションが読める場所 (scratchpad など) へコピーして、そちらを publish する。Artifact ツールが無いセッションなら、
   使えないと伝えて story.html のパスを返す。

コードへのリンクは、`origin` が GitHub で、指す側のコミットが `origin` に push 済みのときだけ付く。

## 主題と図の規則

### 主題の分け方

- 主題は「読む人が 1 つの仕組みとして覚えるもの」で切る。ファイルや関数の単位で切らない。
  1 つのファイルが 2 つの主題にまたがってよいし、1 つの主題が 5 つのファイルを持ってよい。
- 主題の数は、変更が持つ仕組みの数に合わせる。小さな変更は 1〜2、大きくても 6 程度。
- 並べる順は、読む人が理解を積み上げられる順 (土台になる仕組みが先、それを使う流れが後)。
- テスト・版番号・ドキュメントだけのファイルも、どれかの主題の files に入れる。それが検証・説明している
  主題に入れるのが基本で、どこにも当てはまらなければ「テストと版」のような主題を図なしで 1 つ作る。

### 図の選び方

主題ごとに、その変更の**仕組み**が見える形を選ぶ。名前を箱に入れて並べるだけの図は描かない。

| 変更の形 | 図 |
|---|---|
| 呼び出しの順序が変わった・段が増えた | シーケンス (縦の線に、窓・worker・ファイルなどの担い手) |
| 分岐が増えた・判定が変わった | 判定の木 (問いを縦に、答えを横に) |
| 置き場所・繋がりが変わった | 前と後 (左右に並べ、変わった線だけに色) |
| 状態が増えた・移り方が変わった | 状態遷移 (状態を箱、入力を矢印のラベル) |
| データの形が変わった | 型の前後 (欄を行にして、増えた欄だけに色) |
| 処理が回って戻る | 流れとループ (戻る矢印に、止まる理由のラベル) |

- overview は必須。ページの冒頭で「何が変わったか」を 1 枚で言う図。多くの場合は前と後。
- 振る舞いが変わる主題は図を 1 枚以上描く。図なしでよいのは、テスト・版・ドキュメントだけの主題。
- **増えた・変わったところに色を付ける**。図の中で色が付くのは、その主題が言いたいところだけ。
  新しく増えた線と箱は `new`、消えたものは `gone` (点線にして残す)、気をつける分岐は `hold`。
- 矢印には何が起きるかを短く書く (「書く」「≤5s 待つ」「リンクを置く」)。ラベルの無い矢印は描かない。
- 図に載せる語は、コードの名前 (`ReopenAs`) と利用者の呼び方 (「A キー」) を両方使ってよい。
  ただし図が名前の一覧になったら、それは仕組みを描いていない。
- caption は、その図が言っていることを 1〜2 文で。図の中に説明の文を書かない。
- before_after は、図にするまでもない対比 (候補の条件・返す型が変わった、など) に使う。
- excerpts は、主題の要になる数行だけを指す。全部を載せない。読む人が図を見て「本当にそうか」を
  確かめたくなる行を選ぶ。

### SVG の描き方

スクリプトは SVG の中身を検査せず、書いたままページに埋める。だから次を守る。

- `<svg viewBox="0 0 W H" role="img" aria-label="図が言っていること">` で始める。width / height は書かない
  (ページが幅に合わせて縮める)。横の流れは W を広く、縦の積み重ねは H を高く。
- 色はページが用意する class だけで付ける。`fill="#..."` や `stroke="black"` を書かない (ダークで消える)。
  - 箱: `box` (地の色と線)、`soft` (薄い面)
  - 線: `edge` (矢印の線。fill は無い)、`dash` (点線)、`lane` (シーケンスの縦線)
  - 文字: 何も付けなければ本文の色、`sub` (薄い小さな字)、`m` (等幅)
  - 意味の色: 線と枠に `new` / `gone` / `hold`、文字に `newt` / `gonet` / `holdt`
  - 矢印の頭は `<defs><marker>` に `<path d="M0,0 L10,5 L0,10 z" fill="currentColor"/>` で作る。
    色付きの矢印には `class="newt"` などを付けた path の marker を別に作る。
- id はページ全体で 1 つに決まるよう、主題の番号を前に付ける。番号はページの見出しと同じで、themes の 1 つ目が `t1`、overview が `t0`
  (`t2-arrow`、同じ主題に図が 2 枚あれば `t2-2-arrow`)。
  2 枚の図が同じ id を持つと、後の図の矢印が前の図の marker で描かれる。
- `<text>` の中の `<` `>` `&` は `&lt;` `&gt;` `&amp;` と書く。`Vec<String>` をそのまま書くと、ブラウザは
  `<String>` を知らない要素として読み、字が消える。
- `<script>` `<style>` `<foreignObject>` `<a>` `<image>` と、HTML の要素 (`<br>` `<div>` など) を入れない。
  `<style>` はページ全体に効いて他の図と本文を書き換え、HTML の要素は SVG の外へ抜け出す。
- 文字は 11〜13px 相当。座標は格子にそろえる (箱の上下・間隔を同じに)。長い文は箱に入れない。

### concerns

`blocking` は「この中身のまま approve できない理由」、`nonblocking` は「止めないが、読む人が知っておくと
よいこと」。両方とも 1 件 1 文で、`how` にどう確かめたかを書く (`読んだ` / `走らせた` / `測った` /
`確かめられなかった`)。

- blocking に書く前に 1 件ずつ篩う。依頼や計画で決まった仕様の帰結、既存の同種の実装と同じ挙動は外す。
  その場で確かめられること (テストを書く・走らせる・既存の実装を読む) は、確かめてから書く。
  確かめようとして確かめられなかったことが LGTM を止めるなら、how を `確かめられなかった` にして書く。
- 篩で外したもののうち、読む人が知っておくとよいもの (挙動が変わる帰結、測っていない性能) は nonblocking に回す。
- 好みの言い換えや、確かめていない「〜かもしれない」で埋めない。
- blocking が空なら、ページに「止めるものは無い」と出る。読んでいない主題があるのに空にしない。

### story.json の形

```json
{
  "title": "1 行の見出し。何が変わったか",
  "summary": "2〜3 文。前はどうで、後はどうか。マークダウン可",
  "overview": {"svg": "<svg ...>...</svg>", "caption": "この図が言っていること"},
  "themes": [
    {
      "title": "主題の見出し",
      "kind": "図の種類の短い名前 (シーケンス / 判定の木 など)。省略可",
      "body": "2〜4 文。図の読み方。マークダウン可",
      "figures": [{"svg": "<svg ...>...</svg>", "caption": "この図が言っていること"}],
      "before_after": {"before": ["前の 1 文"], "after": ["後の 1 文"]},
      "excerpts": [{"path": "リポジトリ相対のパス", "side": "new | old", "start": 1, "end": 3}],
      "files": ["この主題に入るファイルのパス"]
    }
  ],
  "concerns": {
    "blocking": [{"text": "1 件 1 文", "how": "読んだ | 走らせた | 測った | 確かめられなかった"}],
    "nonblocking": [{"text": "1 件 1 文", "how": "読んだ"}]
  }
}
```

- figures・before_after・excerpts・concerns は省略できる。files は全ての主題に要る (空の配列でもよい)。
- excerpts の side は `new` なら追加行の後像行番号、`old` なら削除行の前像行番号。範囲に変更行が 1 行も
  無いと exit 2。範囲の中の変更行と、その前後 3 行が載る。改名したファイルは old の行も新しいパスで指す。
- files のパスは prepare の一覧どおり。改名したファイルは新しいパスで書く。

### 守ること

- 振る舞いの根拠はコード。図はコードを読んで確かめた流れだけを描く。読んでいない呼び出し先を
  それらしく描かない。確かめられなかった繋がりは図に描かず、本文にそう書く。
- コメントやドキュメントの主張がコードと食い違っていたら、コードを採ったうえで、食い違いを本文に書く。
- 分からないことを埋めない。
- 日本語で書く。

文章の口調は、このセッションの口調のままでよい。ただし口調が変わっても、上の事実の確かめ方は
一切ゆるまない。JSON の形・キー・how の値は変えない。
